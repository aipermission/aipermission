# S3-Compatible Storage

AIPermission's built-in S3 connector supports direct and SSH-tunneled access
to one S3-compatible bucket. Credentials stay in the encrypted local database;
agents receive target/profile/action metadata, never the access-key secret.

## Connection

Create an S3 connector target with:

- endpoint scheme, host, and port;
- SigV4 region and bucket;
- path-style addressing when required by the provider;
- Direct or Over SSH transport; and
- an access-key credential profile with optional temporary session token.

Use **Test connection** before opening the connector workspace. The selected
credential's bucket policy remains the final service-side authority.

## Object Browser And Transfers

The object browser lists folder-like prefixes, exact objects, metadata, and
bounded pages. The Files dialog supports multi-file upload, recursive prefix
download, folder upload, queue ordering, progress, pause/resume, and cancel.

Prefix and search inputs are drafts until Search or Refresh succeeds. Load more
uses the prefix/search snapshot that produced the displayed rows and cursor,
not unapplied edits. Starting a new first-page request retires its old cursor;
a failed reset keeps the previous rows for inspection without appending pages
from the discarded cursor. A failed continuation can be deliberately retried
with the same loaded query. Navigation and visible listing statistics use the
loaded query as well.

Delete confirmations retain the exact object key and optional ETag reviewed
when opened. A pending confirmation accepts one submission at a time. Switching
target/session or opening a replacement confirmation retires its UI ownership;
late action or refresh results cannot close, unlock, or rewrite the replacement.
This does not cancel or prove the outcome of an already dispatched deletion:
consult activity/history before deliberately retrying an uncertain operation.

Current transfer guardrails:

- maximum 100 objects and 1 GiB per batch;
- maximum 512 MiB per object;
- multipart upload above 16 MiB, using 8 MiB parts;
- each multipart part retries transient transport, 408, 429, and 5xx failures
  at most three times with the same upload id and part number;
- overwrite disabled unless explicitly selected;
- failed or canceled multipart uploads are aborted; and
- pause/resume survives only while the current gateway process remains alive.

Downloads are staged locally only for the active bounded transfer workflow.
Completed ZIP downloads preserve supported object-key hierarchy.

Object keys and prefixes are opaque identities: spaces (including whitespace-only
keys), leading/repeated slashes, Unicode, and dot segments are never trimmed or
filesystem-normalized. Providers may reject particular spellings; AIPermission
does not retry with a different key. Versions and temporary URLs use the same
exact key. Use a client that preserves the URL path when consuming a signed URL;
clients that normalize dot segments can invalidate its signature.

Object and version listings request URL encoding so keys containing characters
that XML cannot represent can still be listed. Resource names are decoded once
only when the provider declares this encoding; malformed encoded names fail the
listing. Literal `+` signs are preserved. Continuation tokens and version IDs
remain opaque and are never URL-decoded. Pass raw listing cursors unchanged,
including whitespace, through both actions and Files pagination. See the
provider contracts for
[ListObjectsV2](https://docs.aws.amazon.com/AmazonS3/latest/API/API_ListObjectsV2.html)
and [ListObjectVersions](https://docs.aws.amazon.com/AmazonS3/latest/API/API_ListObjectVersions.html).

The Files dialog uses a virtual locator consisting of `/` followed by the exact
key: `/invoice` addresses `invoice`, while `//invoice` addresses `/invoice`.
`/` alone is the bucket root. Prefix navigation preserves repeated slashes.
Upload `relative_paths`, or the original multipart filename when omitted, are
joined without cleaning; they are remote identities, not local staging paths.

Files transfers reject control characters, invalid UTF-8, keys over 1024 bytes,
and trailing-slash objects. Browsing retains trailing-slash objects, including
zero-byte folder markers, as file entries with their exact paths; selecting them
for transfer fails before mutation without blocking other files or navigation.
Recursively expanding a prefix containing them fails explicitly rather than
silently dropping them; select individual supported files instead.
Structured object actions remain available
subject to their own size limits and provider support; they do not use the Files
transfer path validator. Single downloads use a separate safe local filename,
reported in the transfer record, without changing the remote key.

ZIP batches reject keys whose hierarchy the archive writer would rename: empty
or dot-prefixed components, trailing component whitespace, trailing dots,
components longer than 160 characters, and backslashes or `:<>"|?*`. Download
such objects individually instead. Rejection occurs before the batch starts;
the gateway does not silently flatten or rename these keys inside a ZIP.

## Temporary URLs

`presign_download` and `presign_upload` create a signed URL for one exact key.
Expiry is limited to 60–3600 seconds. Upload URLs reject an existing key unless
overwrite was explicitly approved.

When `presign_upload` returns `required_headers`, the uploader must send every
listed header unchanged. In particular, no-overwrite URLs require
`If-None-Match: *`; that header is part of the SigV4 signature and makes reuse
or a concurrent object creation fail instead of replacing the object.

A signed URL is a temporary bearer credential. Anyone holding it can perform
the signed operation until expiry. Do not place it in reasons, reusable config,
public logs, or unrelated messages.

## Object Versions

`list_object_versions` returns bounded pages for one exact key, including
delete markers. Restoring a stored version copies it into a new current
version; it does not erase the current history. Deleting an exact version or
delete marker is permanent and is classified as destructive.

These controls require bucket versioning support from the S3 provider. When
versioning is disabled or unsupported, the provider may return an empty list or
an explicit API error.

Exact-version deletion uses the immutable `version_id`; historical version
ETags are not sent as delete preconditions because S3 conditional delete
headers apply to the current object state.

S3-compatible providers do not all implement destination conditional headers
with identical semantics. **Verified conditional requests** is off by default.
Enable it only after provider documentation or conformance testing confirms
destination `If-Match` and `If-None-Match`. AIPermission fails closed while the
setting is off: no-overwrite uploads and presigned uploads, ETag-guarded writes
or deletes, and version restores are rejected before dispatch. The setting does
not change approval policy and does not block explicitly unguarded operations
such as `overwrite=true` uploads or deletes without an ETag. Those operations
remain non-idempotent and should remain Prompt unless the operator knowingly
accepts their risk.

Multipart retries are limited to an individual part whose remote identity is
fixed by upload id and part number. Cancellation, deadline expiry, and
non-transient 4xx responses are not retried. Multipart completion is never
automatically retried after an uncertain response; the gateway reports
`outcome_unknown` instead.

## Lifecycle Policy

The lifecycle dialog reads and summarizes the current policy while retaining
the provider's raw XML for inspection. AIPermission intentionally does not
attempt a lossy merge of arbitrary provider-specific lifecycle XML.

An empty policy is reported only when the service returns HTTP 404 with the
exact `NoSuchLifecycleConfiguration` error code. A missing bucket, an uncoded
404, permission denial, transport failure, or provider outage remains an error;
error-message text alone is never treated as proof that a policy is absent.

`replace_bucket_lifecycle` replaces the complete policy with exactly one
bounded expiration/cleanup rule. `delete_bucket_lifecycle` removes the complete
policy. Both are destructive and should remain Prompt-first. Always read and
review the existing policy before either action.

The replacement rule can scope one object prefix and independently configure:

- current-version expiry days;
- noncurrent-version expiry days; and
- incomplete multipart upload cleanup days.

Use `0` to disable an individual behavior; at least one behavior must be
enabled. Day values are bounded to 36,500.
